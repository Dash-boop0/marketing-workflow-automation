How it works

The same pipeline runs in the browser, on the command line and as an n8n workflow.

How the workflow runs

  1. Ingest – parse the CSV (RFC 4180: quotes, commas and line breaks inside quotes, BOM, CRLF) and map header aliases.
  2. Validate – required fields, email syntax, date formats and more. Each rule either rejects the row or warns and keeps it (table below).
  3. Normalise – trim, title-case names, lower-case email, phone to digits with country calling code, country to ISO code, source names to a fixed list.
  4. Dedupe – same email first, then same first name + last name + company. The first row survives; blank fields are filled from duplicates; any opt-out wins.
  5. Categorise – ordered rules from the rules file assign a category and priority; first match wins, otherwise the default.
  6. Tasks – one follow-up task per lead with a due date offset by priority (optionally skipping weekends).
  7. Mock messaging – logs the email that would be sent for opted-in leads. Nothing is sent; there is no sending code.
  8. Outputs – clean leads, rejected rows with reasons, tasks, mock outbox, run log (JSON) and a summary (Markdown).

Idempotency

Record IDs are a hash of the normalised email (or name + company), task IDs a hash of the record ID. Re-running the same input with the same rules and run date produces identical outputs. With the saved task board on, a re-run inserts only tasks that do not exist yet, keeps your status changes, and does not repeat mock messages.

Same logic on the command line

node cli/run.js --input sample-data/leads.csv --rules config/rules.json --out out/ --today 2026-10-20
